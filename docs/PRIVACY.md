# Privacy: what Moly stores, where, and how it is removed

Audited 2026-10-12 (tests named below keep it true).

## What is stored, and where
- **Database**: `~/.moly/moly.db`, encrypted with SQLCipher (AES-256). The key lives in the operating system's keychain (or `MOLY_DB_KEY`). Where there is no keychain, the person chooses on first start (`keystore/`, `keygate.go`): a passphrase that seals the key (scrypt + AES-GCM, asked at every start, wrong guesses slowed to 5 s) or, after an explicit confirmation, a key file (`~/.moly/db.key`, mode 0600, which protects only against other users). Nothing is chosen silently, and a key is never replaced while a database exists. `keystore.json` records the choice; if the keychain or key file later disappears, Moly says so instead of making a new key. The directory is `0700` and the database files `0600`, and the process umask is `0077`, so new files (write-ahead log, shared memory) are private from the start (`database.HardenDataDir`).
- **Per user**: account (email, bcrypt password hash), sessions (24 h), conversations and chat messages, per-message summaries, conversation summaries, people and their traits, goals and facts (`context_attributes`), clarification questions and answers, reflections, safety incidents, metrics. Every table that can hold user data has a `user_id` (or a `conversation_id` or a foreign key that leads to one).
- **Browser**: the session of the local profile (no password) in `localStorage`; the session of an account (development backend with a login) only in `sessionStorage`, which the browser discards when the panel closes, so reopening Moly asks for the login again (`stores/authStore.ts`); the cached About Me profile and error reports in `localStorage`; extension data in `chrome.storage.local`.
- **Install screen (extension 0.1.1):** when the app is missing and the user presses "Download latest version" on Windows, the extension asks `api.github.com` for the newest installer file name (one GET, no user data; GitHub sees the IP address). Linux and Mac show a copyable command and make no request. The extension has no host permission for this.
- **Card feed (0.1.2, extension and phone):** at most once a day the app fetches `https://nireus79.github.io/Moly/cards.json` (card text; no cookies, no referrer, nothing about the user; validated; cached; built-in card as fallback).
- **Third parties**: to write a reply, the text of the turn is sent to the model the user configured: a local Ollama model, or Anthropic, or OpenAI. Nothing else leaves the machine.

## What is never stored
- **Secrets** the user types. Card numbers (Luhn) and IBANs (mod 97) are cut out by their shape before any model call, summary or save. Passwords, PINs, ID numbers and keys are listed by the extraction (`sensitive`) and cut out of the message and of everything derived from it before the intent, the reply and every save (`tools/redact.go`, `agents.ScrubSensitive`; scenario S57).
- **Anything learned from a refused message**: no people, no goal, no per-message summary, no facts, no saved entities (S49, S51). Kept for audit: the two chat lines and the safety incident.
- **User content in the log.** The standard logger writes through a scrubber (`privacy` package): the message, the goal, names, traits, quotes, gaps, questions, summaries and Moly's replies are registered as the server learns them and masked in every later log line. `MOLY_LOG_CONTENT=1` turns the masking off for debugging. Test `TestLogsHoldNoUserContent`; a live run with unusual words found none of them in 893 log lines.

## API keys (cloud providers)
- **Where, and whose:** the provider, model and API key belong to the user. They are saved in the backend's encrypted database (tables `user_ai_settings` and `user_ai_keys`, one set per user). One user cannot read, use, replace, unlock or delete another user's; a user with no key of their own gets no provider, never someone else's. The extension does not keep the key. Every model call is made through the provider of the user it is made for (`tools.LLMSource`, `llm_settings.go`); a call with no user fails. The tables are never exported and go with the profile. The environment is not a second source: `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` never replace or supply a user's key. Only `LLM_PROVIDER` set by whoever starts the program (a developer or a test run) fixes one provider for every user of that run, and the settings are then read-only.
- **Older versions** saved one set of settings for the whole installation. The local profile (the one person of an installed Moly) takes them over once; no other user can.
- **Passphrase protection (recommended):** with a passphrase the key is sealed (scrypt, about 100 ms per guess, then AES-256-GCM) before it is saved. The database key sits in the operating system's keychain, where a program running as the same user may be able to read it; the passphrase is not stored anywhere, so a copied database, a backup, or malware that reads the keychain gets ciphertext only. After every start of the backend the user unlocks the key once; it is then held in memory only. Wrong guesses are slowed down (1 to 5 seconds each).
- **Never returned, never logged:** no endpoint returns a key (the settings answer only says whether one is stored and whether it is sealed); the log scrubber masks it; provider error text is cleaned of it. Test: `TestLLMSettings*`, `TestApiKeyIsNotReadableInTheDatabaseFile`.
- **Process hardening (Linux, production mode):** the backend marks itself non-dumpable, so other programs of the same user cannot read its memory through ptrace or `/proc/<pid>/mem`. macOS and Windows have no equivalent yet.
- **What this cannot do:** nothing protects a key from malware that logs keystrokes (it sees the passphrase), runs as administrator, or reads the process while it is unlocked on a platform without the hardening. Advice for users: create a separate API key for Moly with a spending limit at the provider, and use Ollama if no key should ever exist.

## Deleting a profile
`DELETE /api/user/delete` with the password (bcrypt check). In one transaction it deletes every row of every table with a `user_id`, every row of tables keyed only by conversation, and the rows that hang from the user's rows through foreign keys, then the user. A table added later is covered because the tables are found from the schema. Afterwards it truncates the write-ahead log and compacts the file (`VACUUM`), `secure_delete` is on for every connection, the user's sessions are gone with the user, and the server drops the user's in-memory state (saved conversation states, skip offers, learning agent, the log scrubber's list). The extension clears `chrome.storage.local`, `localStorage` and `sessionStorage`. On logout it removes the cached About Me profile and the error reports.
Tests: `TestDeleteUserLeavesNothingInAnyTable` (fills every table for a user and a bystander, deletes, scans every cell), `TestScenarioS58ProfileDeletionRemovesEverything` (through the handler: wrong password deletes nothing, the right one leaves no row mentioning the user, the old token fails, memory is empty, another user is untouched), `TestSecureDeleteIsOnForEveryConnection`.

## Known gaps (decisions open)
- Export exists (`GET /api/user/export`, button "Export my data" in Settings): one JSON file with every table that holds the user's rows, found from the schema like the deletion; password hash and session tokens are left out (`TestScenarioExportHoldsMyDataAndOnlyMine`). Such a file can be restored with Settings, "Import data..." (`POST /api/user/import`) into an empty profile: the whole file is checked before anything is written, table and column names must exist in the schema, every restored row gets the new profile's id, and a file that does not fit changes nothing.
- The safety judgement, the meta-instruction call and the extraction itself read the raw text of a message once (they are how secrets are found); a refused message's incident row holds the shape-redacted text.
- The long extraction prompt (`MOLY_EXTRACT_PROMPT=long`) does not list secrets.
- Raw refused text stays in the safety incident table until the profile is deleted (no retention limit yet).
- Production items: in development mode the server listens on all interfaces, with `Access-Control-Allow-Origin: *` and no TLS. Production mode (`MOLY_PRODUCTION=1`, see `security.go`) listens on 127.0.0.1 only, answers only the allowed extension origins, checks the Host header, and needs a per-run token (`X-Moly-Token`, file `~/.moly/session.token`, mode 0600). Sessions are still plain random tokens in the `sessions` table.
- Old plaintext database copies on a developer machine are outside the program's control (see the audit note for 2026-10-12: `~/.moly/*.bak*`, `*-test-lifecycle.db`).


## The memory (2026-10-16)
The memory tables (`memory_people`, `memory_roles`, `memory_traits`, `memory_questions`, `memory_facts`, `memory_goals`, `memory_mentions`, `memory_ops`) hold what the user told Moly about people, themselves and their aims, with the exact words each fact came from (`memory_ops.op`). They carry `user_id` or `conversation_id`, so profile deletion and conversation deletion remove them (`TestDeleteUserLeavesNothingInAnyTable`, `TestMemoryOfAConversationLeavesWithTheProfile`); a named person another conversation mentions stays when one conversation is deleted. Export and import find the tables from the schema. The update call never sees a secret the extraction found: the update is run on the message without it (S57). `MOLY_LOG_CONTENT=1` shows content in the log for debugging and is ignored in production mode.


## The Android app (2026-10-21, `moly-mobile/`)
- **Storage:** the app's private files directory (`HOME` of the engine). The same SQLCipher database; its 32-byte key is generated on first start, wrapped with an Android Keystore AES-GCM key and kept in the app's private preferences (`KeyHelper`), and handed to the engine in `MOLY_DB_KEY`. `android:allowBackup="false"`: no cloud or device-transfer backup. Uninstalling deletes everything. "Save a copy" and "Restore from a copy" use Android's own save and file pickers (`MolyEnginePlugin.saveFile/pickFile`); the AI key is not in the copy (same export as the desktop).
- **Network:** `INTERNET` for the provider calls, the loopback link and the card feed (at most once a day, `https://nireus79.github.io/Moly/cards.json`: card text only; no cookies, no referrer, nothing about the user; validated; cached; built-in card as fallback). The engine listens on 127.0.0.1 on a random port chosen once per install (20000 to 31999, kept by the page, saved by the plugin: `EnginePort`), so another app or copy of Moly cannot already hold it; production mode needs the per-run token (`X-Moly-Token`) from `files/.moly/session.token`, readable only by the app. Another app could still connect to the loopback port, but is refused without the token. The `foss` build contains no ad, billing or analytics code. `network_security_config` allows cleartext only to 127.0.0.1.
- **Other permissions:** `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `POST_NOTIFICATIONS` (the "Moly is running" notice). No storage, contacts, location, camera or microphone permission. The share receiver accepts `text/plain` only and holds the text in memory until the screen takes it.
- **Logs:** `files/heartbeat.log` (service and engine events, capped at 200 KB; no content) and `files/engine.log` (the engine's log with its content scrubber, capped at 1 MB). "Report a problem" builds a text from the first and the error lines of the second (cut to 200 characters, key-like strings masked); the screen shows it in full and it leaves the phone only through the share sheet when the person taps Share.
- **Checked on the emulator (2026-10-21), not yet on a phone:** a turn with unusual words (a name, a company-like word, a place) and a password-like string left none of them in `engine.log` or `heartbeat.log`, nor in the report text. The stand-in model returned no extraction, so names the model would learn were not registered with the scrubber in that run; the desktop test `TestLogsHoldNoUserContent` and the earlier live run cover those. Android's system log (`logcat`) did hold the message text in a **debug** build, because Capacitor prints plugin calls and the web console when the app is debuggable; a **release** build prints nothing from the screens (Capacitor's default `loggingBehavior` is `debug`: only debuggable apps log). Checked at start-up and during health checks on a release build, not during a send.
