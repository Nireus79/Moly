WHAT RISKS EXIST
================================================================================

RISK 1: Multi-Pass Parsing Removal (CRITICAL → LOW with testing)
  Problem: Removing re-parsing might miss nuances
  Solution: Use LLM confidence scores, ask clarification for low confidence
  Mitigation: 5 unit tests, compare single-pass vs multi-pass accuracy
  Effort to rollback: 1 day

RISK 2: Orchestrator Consolidation (HIGH)
  Problem: 11 layers → 1 layer might miss edge cases
  Solution: Build in parallel, use feature flag (10% → 50% → 100%)
  Mitigation: 20 integration tests, A/B testing, monitor skip rates
  Effort to rollback: < 1 hour (flip flag)

RISK 3: Response Validation (MEDIUM)
  Problem: Constraints might block valid responses
  Solution: Two levels (HARD block vs WARN + ask user)
  Mitigation: Monitor violation rate < 5%, human review samples
  Effort to rollback: < 1 hour (flip flag)

RISK 4: Database Migration (HIGH)
  Problem: Schema changes could corrupt production data
  Solution: Dual-write phase, staged cutover, rollback migration
  Mitigation: Test on copy of prod DB, monitor data consistency
  Effort to rollback: 2 hours (migration + verification)

RISK 5: LLM Constraint Handling (MEDIUM)
  Problem: LLM might ignore constraints or timeout
  Solution: Retry with relaxed constraints, fallback to clarification
  Mitigation: Add retry logic, confidence threshold checks
  Effort to rollback: < 1 hour (flip flag)

RISK 6: Performance Degradation (MEDIUM)
  Problem: Validation adds latency
  Solution: Cache constraints, async validation, benchmark before/after
  Mitigation: Keep p95 latency < 3 seconds, 20% increase tolerance
  Effort to rollback: < 1 hour (flip flag)

KEY DECISION POINTS (Go/No-Go Gates)
================================================================================

After Phase 1 (Week 3): Proceed to Phase 2?
  GO IF:    Lock enforcement working, no multi-pass parsing bugs
  NO-GO IF: Lock enforcement causes regressions, accuracy loss
  Risk:     LOW - can be done safely, easy rollback

After Phase 2 (Week 6): Replace old layered system entirely?
  GO IF:    Orchestrator handles all question types, rollout stable at 100%
  NO-GO IF: Orchestrator misses question types, crashes on edge cases
  Risk:     HIGH - consolidation is biggest refactor, requires testing

After Phase 3 (Week 9): Enable constrained generation for all users?
  GO IF:    Constraint violation rate < 5%, latency increase < 10%
  NO-GO IF: Constraints cause timeouts, false positives, quality degrades
  Risk:     MEDIUM - fallback mechanisms in place

After Phase 4 (Week 12): Keep new schema permanently?
  GO IF:    Data migration clean, no corruption, queries performant
  NO-GO IF: Data corruption found, queries slow, overhead too high
  Risk:     HIGH - migration is irreversible, but rollback tested

WHAT GETS BETTER
================================================================================

BUG: Role Reversal (CRITICAL FIX)
  Before: "User: I'm dominant" → "Moly: explore your submissive nature" ✗
  After:  Response validated against facts, never contradicts ✓
  Impact: Impossible to happen anymore

BUG: Repeated Questions (ANNOYING FIX)
  Before: Same question asked twice in same conversation
  After:  Deduplication checks, no repeated questions
  Impact: Better user experience

ISSUE: Mysterious Questions (UX FIX)
  Before: "Why is Moly asking this?"
  After:  Every question logs principle basis and reason
  Impact: Transparency + trust in system reasoning

ISSUE: Slow Clarification Loop (PERFORMANCE FIX)
  Before: 2-3s average latency per message
  After:  1-2s average (consolidated logic, parallelization possible)
  Impact: Faster interactions

CODE QUALITY: Maintenance (DEVELOPER FIX)
  Before: 1500 LOC scattered across 5 files
  After:  300 LOC in 1 orchestrator
  Impact: 5x easier to maintain/modify

RECOMMENDATION
================================================================================

✅ START WITH PHASE 1 (LOW RISK, HIGH VALUE)

Why Phase 1 first?
  1. Fixes multi-pass parsing (root cause of bugs)
  2. Takes only 3 weeks (low time commitment)
  3. Very low rollback risk (1 day)
  4. Can run with rest of system unchanged
  5. Validates extraction-locking approach before full redesign

If Phase 1 succeeds → Phase 2 unlocks real value (orchestrator consolidation)
If Phase 1 fails → Only 1 week lost, system remains functional

Timeline:
  Phase 1:  3 weeks (low risk)
  Phase 2:  3 weeks (high value, with feature flag)
  Phase 3:  2 weeks (medium risk, with flag)
  Phase 4:  3 weeks (high risk, carefully staged)
  Total:    11 weeks for full redesign

Fallback: If any phase hits critical risk, stop and keep working system.
Current system is stable; redesign is about eliminating complexity and bugs.
